# Single manager role: scope as data, not rank

ADR 0001 renamed the role ladder to `student < staff < team_manager < department_manager < admin`, but the two manager-shaped roles still differed only in scope — one managed a department (old "location"), one managed a team (old "department") — while the rank ladder pretended one outranked the other. Once scope moved into the schema as `departments.manager_id` / `teams.manager_id` FK columns, the role split had nothing left to express: both collapse into a single `manager` role (ladder `student < staff < manager < admin`), the `scheduler` role disappears, and team-vs-department authority is enforced by which entities point at the caller, with a department-scope guard on department-level actions (creating teams, jobs, workers) where rank used to do the separating.

The same pass moved scope out of assignment side-tables (`manager_assignments`, `scheduler_assignments`, `student_assignments` — deleted) into `manager_id` columns, so a manager can hold several teams and/or departments while each team/department has exactly one manager; worker→team membership became a `worker_teams` join table (a worker may be in several teams, and membership — not job rows — is what makes a worker visible to a manager); the API JSON keys followed the schema (`locationId`→`departmentId`, `departmentId`→`teamId`) so no layer reads backwards; and all Postgres objects moved from `public` into a named `scheduling` schema (`search_path=scheduling`). This is a greenfield rework: the schema is rewritten in a single migration and dev databases are wiped, rather than ALTERed. Considered keeping the two named roles from ADR 0001; rejected because with scope in data, a second manager role would only re-create the vocabulary confusion the rename was fixing — the role-name half of ADR 0001 is superseded, its scope-entity rename (`locations`→`departments`, `departments`→`teams`) stands.
